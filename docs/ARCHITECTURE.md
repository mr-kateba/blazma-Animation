## 3. طبقة الأوامر الموحدة (Command Layer)

كل تعديل يمر عبر المسار نفسه:

```
UI         → CommandBus.Execute(cmd) → Core
Claude/MCP → CommandBus.Execute(cmd) → Core
Codex/CLI  → CommandBus.Execute(cmd) → Core
```

```csharp
public interface ICommand {
    string Id { get; }                 // "keyframe.add"
    CommandEffect Effect { get; }      // ReadOnly | Mutating | Destructive | External
    CommandResult Execute(CommandContext ctx);
    void Undo(CommandContext ctx);     // إلزامي إذا كان Effect != ReadOnly
}

public sealed record CommandResult(
    bool Ok, JsonNode? Data, IReadOnlyList<Change> Changes,
    IReadOnlyList<Diagnostic> Warnings, ErrorInfo? Error);
```

- **الأوامر الطويلة (Jobs):** التوليد بالـAI والتصدير والتحليل الثقيل لا تكون `ICommand` متزامنًا. تُنفَّذ كـ`IJob` غير متزامن يقبل `CancellationToken` ويرسل تقدّمه (يتحول إلى MCP progress notifications)، ويعمل على **لقطة غير قابلة للتعديل** من المشروع. عند الانتهاء ينتج أمر `Apply` متزامنًا قابلًا للتراجع.
- **دمج الأوامر أثناء السحب:** سحب Gizmo أو منحنى يفتح Transaction (`Begin/Update/Commit`)، فيصبح السحب كله خطوة Undo واحدة.
- **ما لا يدخل Undo:** التحديد، الكاميرا، موضع رأس التشغيل، تخطيط اللوحات.
- **مكدّس Undo واحد مشترك** بين الواجهة وMCP وCLI. كل Transaction يحمل `id` ومصدره (ui/cli/mcp + معرّف جلسة الوكيل). `edit_undo` من الوكيل يأخذ `transactionId` إلزاميًا، فلا يستطيع الوكيل التراجع عن تعديل المستخدم بالخطأ.
- **سجل الأوامر (Command Registry):** كل أمر يعلن اسمه، مخطط مدخلاته (JSON Schema)، مخطط مخرجاته، تأثيره، ووصفه.
  تُولَّد منه تلقائيًا: أدوات MCP، أوامر CLI الفرعية، ووثيقة `MCP_TOOLS.md`. **مصدر الحقيقة واحد.**
- **Undo/Redo:** مكدّس أوامر لكل مشروع. العمليات المركبة (مثل توليد حركة بالـAI) تُجمَّع في `CompoundCommand` واحد يمكن التراجع عنه بخطوة واحدة.
- **سجل العمليات:** كل أمر يُسجَّل في `oplog.jsonl` داخل **مجلد الجلسة** (وليس داخل الأرشيف)، مع المصدر والزمن والنتيجة. للسجل حد أقصى للحجم ويُدوَّر تلقائيًا، ولا يُضمَّن في ملف المشروع إلا إذا اختار المستخدم ذلك، لأنه قد يحتوي على Prompts ومسارات.
- **الإشعار بالتغيير:** `Changes` تحدد ما تغيّر (مقطع، مسار، نطاق زمني)، فتعيد الواجهة رسم الأجزاء المتأثرة فقط ولا تعيد حساب الحركة كاملة.

## 4. نموذج العمليات (Process Model)

| الوضع | الوصف |
|---|---|
| تطبيق مفتوح | يفتح Godot خادم IPC محليًا (Named Pipe على Windows، Unix socket على Linux). عند تشغيل `blazma-mcp` أو `blazma-anim --attach` يتصل بالتطبيق ويرسل الأوامر نفسها، فتظهر التعديلات مباشرة مع Undo. |
| بدون واجهة (Headless) | CLI/MCP يحمّلان المشروع مباشرة عبر المكتبات وينفذان الأوامر ثم يحفظان. يُمنع فتح المشروع نفسه من عمليتين للكتابة عبر ملف قفل `.lock`. |
| توليد الحركة | `kimodo-runner` عملية منفصلة (C++) يُطلقها التطبيق عند الطلب فقط. الانهيار أو نفاد الذاكرة لا يُسقط المحرر، والإلغاء يتم بإنهاء العملية. لا تُحمَّل أي نماذج أثناء الخمول. |

الاتصال بين الأطراف بـJSON-RPC 2.0 مع الرسائل نفسها المستخدمة في MCP، فلا توجد صيغة ثالثة.

**الخيوط (Threading):** شجرة مشهد Godot تُعدَّل من الخيط الرئيسي فقط. خيوط IPC تضع الأوامر في طابور، والطابور يُفرَّغ داخل `_Process` على الخيط الرئيسي، فلا تتغير حالة Core أثناء قراءة الـViewport لها. الحسابات الثقيلة تعمل على خيوط عاملة فوق لقطات غير قابلة للتعديل.

**أمان IPC:** على Windows يُقيَّد الـNamed Pipe بقائمة صلاحيات (ACL) للمستخدم الحالي فقط. على Linux يوضع الـsocket في `$XDG_RUNTIME_DIR` بصلاحيات `0600`. خادم MCP يكتب على stdout رسائل البروتوكول فقط، والسجلات على stderr.

## 5. الرياضيات والاصطلاحات

- **الوحدة:** المتر. **المحاور:** نظام يميني (right-handed)، ‎+Y للأعلى، ‎+Z لأمام الشخصية، مثل glTF 2.0.
  - لا حاجة لتحويل محاور عند استيراد glTF إلى Godot. لكن Godot يعتبر ‎−Z اتجاه الأمام للكاميرات و`look_at`، و`Vector3.MODEL_FRONT` = ‎+Z، لذلك يجب أن يستخدم كود IK والنظر `use_model_front`.
  - يجب تعطيل خيارات Godot الخاصة بـRetarget وRest fixer عند الاستيراد، وإلا تتغير وضعية الراحة (rest pose) للعظام.
- **الدوران:** Quaternion بترتيب `(x, y, z, w)` ومُطبَّع، و`q` و`−q` متساويان. زوايا Euler للعرض فقط: ترتيب XYZ **داخلي (intrinsic)**، وقابل للتغيير في الواجهة.
- **الزمن:** عدد صحيح 64-bit بوحدة *flick* (‏1/705,600,000 ثانية).
  - **تم التحقق حسابيًا:** يقبل القسمة بالضبط على 24 و25 و30 و48 و50 و60 و90 و100 و120 إطارًا في الثانية، وعلى معدلات NTSC ‏(24000/1001 = ‏29,429,400 flick لكل إطار، و30000/1001 = ‏23,543,520)، وعلى 44.1 و48 kHz.
  - المعدلات غير الدقيقة (مثل 11 أو 13 إطارًا) تُخزَّن كـFPS نسبي (`num/den`)، وتحويل الزمن إلى إطار يستخدم التقريب لأقرب إطار، مع ضمان أن التحويل ذهابًا وإيابًا يعيد رقم الإطار نفسه.
  - `duration` ونهاية الـloop **حصرية** (exclusive). عند تصدير glTF لمقطع متكرر يُكرَّر المفتاح الأول في النهاية.
- **السماحيات الرقمية الافتراضية للاختبارات (تُحسب بدقة double):**
  - الدوران: ‎1e-4 راديان، والزاوية تُحسب بالصيغة `4·atan2(|q1 − s·q2|, |q1 + s·q2|)` حيث `s = sign(dot)`. لا نستخدم `acos` على float32 لأن دقته لا تكفي تحت ~3.5e-4.
  - الموضع: ‎1e-5 م أو ‎1e-6 من المسافة (أيهما أكبر)، لأن دقة float32 تقل مع حركة جذر طويلة.
  - الزمن: ‎0 flick بعد الحفظ والتحميل، و≤ نصف إطار بعد التصدير.

## 7. الفيزياء المساعدة (المرحلة 6) — `Blazma.Physics`

مكتبة بلا Godot تعتمد على Core وRigging وMotion. كل الحسابات في فضاء النموذج (متر، ‎+Y أعلى، ‎+Z أمام، ‎+X يسار الشخصية) وعلى المقطع **مقيَّمًا من وضعية الراحة** (كما في التشغيل والتصدير)، لا على وضعية العمل. الأوامر في `PhysicsCommands.cs`.

### 7.1 نموذج الكتلة (`MassModel`)
- لكل عظمة مقطع يبدأ من أصلها (المفصل القريب) وينتهي بنقطة بعيدة: المفصل المعياري التالي للعظام المربوطة بالهيكل البشري (الفخذ ← الساق ← القدم ← الأصابع…)، وإلا الابن الوحيد (أو متوسط الأبناء).
- مركز كتلة المقطع: `c = p + r·(d − p)` مثبَّت في إطار العظمة، فيدور معها. النسب `r` من جدول Winter (4.1): الفخذ 0.433، الساق 0.433، القدم 0.5، العضد 0.436، الساعد 0.430، الجذع 0.5، اليد ≈0.35 من طولها (0.506 من الرسغ إلى المفصل الأوسط)، الرأس 0.45.
- العظام الطرفية (الرأس، اليد، الأصابع) تمتد باتجاه العظمة الأم بطول نسبةً من الطول المقدَّر `H = 1.14 × (أعلى مفصل − أدنى مفصل)` في وضعية الراحة: الرأس 0.13H، اليد 0.108H، الأصابع 0.03H.
- الكتل: `Bone.Mass` (الدمية: نسب Winter من 75 كغ). إذا لم تكن لأي عظمة كتلة (Rig مستورد) تُوزَّع كتلة كلية (75 كغ افتراضيًا) بنسبة طول المقطع، ويصدر تحذير `estimated_mass`.
- مركز كتلة الجسم: `COM = Σ mᵢ cᵢ / Σ mᵢ`. للدمية (1.80 م): ≈1.04 م في وضعية T، و≈1.02 م (0.56H) والذراعان إلى الأسفل.
- السرعة والتسارع: فروق محدودة مركزية على الإطارات `v = (x₊ − x₋)/2Δt`، `a = (x₊ − 2x + x₋)/Δt²` (من جانب واحد عند طرفي المقطع).

### 7.2 التلامس ومضلع الارتكاز (`FootModel`، `BalanceAnalyzer`)
- لكل قدم مربوطة خمس نقاط للنعل، مبنية في وضعية الراحة على مستوى الأرض: كعبان (مع عظمة القدم)، نقطتا مشط عند مفصل الأصابع (مع القدم)، ورأس الأصابع (مع عظمة الأصابع). `L` = المسافة الأفقية من الكاحل إلى مفصل الأصابع؛ الكعب ‎0.35L خلف الكاحل، الرأس ‎0.45L أمام مفصل الأصابع، نصف العرض ‎0.38L عند المشط و‎0.23L عند الكعب.
- النقطة تلامس الأرض إذا `y − ground ≤ 0.03 م` **و** سرعتها ≤ 0.35 م/ث. القدم المثبتة (IK pinned) تُعتبر ساكنة. الوضعية المفردة (بلا مقطع) لا تُختبر سرعتها.
- مضلع الارتكاز = الغلاف المحدب ثنائي الأبعاد (XZ) لنقاط التلامس (Andrew monotone chain)، بعكس عقارب الساعة.
- الهامش = المسافة الأفقية الموقَّعة من النقطة المختبرة إلى المضلع: موجبة داخله (المسافة إلى أقرب ضلع)، سالبة خارجه. نقطة أو قطعة فقط ← الهامش ≤ 0.
- النقطة المختبرة (`metric`):
  - `com` (افتراضي، ساكن): إسقاط COM عموديًا.
  - `zmp` (نموذج cart-table): `p = c − (c_y − g)·a / (a_y + G)` للمركبتين الأفقيتين، `G = 9.81`؛ غير معرَّف عند `a_y + G ≤ 0.1G` (سقوط حر) فيُستخدم COM.
  - `capture` (Capture point، LIPM): `ξ = c + v/ω₀` حيث `ω₀ = √(G/(c_y − g))`.
- الحالة: `balanced` إذا الهامش ≥ `minMargin`، `unbalanced` إذا أقل، `airborne` إذا لا تلامس (القفز ليس خطأ توازن). التقرير يجمع الإطارات غير المتوازنة المتتالية في نطاقات مع أسوأ هامش.

### 7.3 Auto-balance (`AutoBalance`)
1. الهدف = أقرب نقطة إلى COM داخل المضلع المنكمش بالهامش (تقاطع أنصاف المستويات)؛ إذا كان المضلع أضيق من ضعف الهامش فمركزه الهندسي (أو أقرب نقطة لنقطة/قطعة).
2. تُثبَّت القدمان الداعمتان على تحويلهما الحالي، ويُزاح الحوض أفقيًا (في فضاء أبيه)، ثم يُعاد حل IK عبر `PoseSolver`.
3. لأن الساقين المثبتتين لا تتبعان الحوض، يتحرك COM أقل من الحوض؛ لذلك تُحل `COM(shift) = target` بتكرار secant مخمَّد (حتى 40 تكرارًا، دقة 1e-6 م)، مع حد أقصى للإزاحة `maxShift` (0.3 م).
4. الأمر يضع مفاتيح: إزاحة الحوض، ودوران عظام الساقين غير المثبتتين في المقطع (thigh/calf/foot)، على الإطارات المصححة، ومفاتيح بالقيم الأصلية على الإطار السابق واللاحق لكل مجموعة مصححة. ثم يعيد تقييم المقطع المعدَّل ويعيد هامش قبل/بعد وانحراف القدمين لكل إطار. خطوة Undo واحدة (`ClipEdit`). مسار الحوض المقفل ← `track_locked`.

### 7.4 المسارات (`Trajectories`)
مصفوفة `Vec3` لكل إطار: COM، الحوض، وكاحلا القدمين، للرسم في الـViewport.

### 7.5 الحركة الثانوية (`SecondaryMotion`)
- لكل عظمة مختارة (الأب قبل الابن) اتجاه محاكى في فضاء النموذج `q` يلاحق الهدف `q* = (اتجاه الأب المحاكى) × (الدوران المحلي الأصلي)`، فيتراكم التأخر على طول السلسلة.
- نابض زاوي مستقل عن الكتلة: `α = k·e − c·ω` حيث `e` متجه الدوران من `q` إلى `q*`. التردد الطبيعي `√k` راديان/ث، ونسبة التخميد `c/(2√k)`. الافتراضي `k = 150`، `c = 12` (≈1.9 هرتز، ζ≈0.49).
- التكامل: خطوات داخلية ثابتة ≤ 1/240 ث مهما كان FPS (الهدف يُستكمل خطيًا بين الإطارات)، وتخميد ضمني `ω ← (ω + h·k·e)/(1 + h·c)` ثم `q ← exp(h·ω)·q`؛ فهو مستقر لأي FPS ولأي `c`، ويتقارب إلى الوضعية الأصلية عند توقفها. التأخر محدود بـ`maxAngle` (30° افتراضيًا).
- النتيجة تُخبز كمفاتيح دوران على كل إطار من النطاق (خطوة Undo واحدة). المسارات المقفلة تُتخطى بتحذير.

### 7.6 القيود المعروفة
- الأرض مستوية أفقية (y = 0 للدمية)؛ لا منحدرات ولا درج. اليدان والركبتان لا تُحسب كنقاط ارتكاز.
- النعل تقريب بخمس نقاط؛ لا تشوه للقدم.
- COM والـZMP من الحركة المفتاحية فقط؛ لا قوى خارجية، ولا ديناميكا عكسية كاملة، والتسارع بالفروق المحدودة حساس للمفاتيح المتقطعة.
- Auto-balance يحرك الحوض فقط (بلا إمالة للعمود الفقري)؛ قد يعجز إذا كانت الساقان ممدودتين تمامًا (`leg_reach`) أو تجاوز `maxShift`. المفاتيح المضافة تغيّر الاستكمال قليلًا بين الإطار المجاور المحمي والمفتاح الأصلي التالي.
- الحركة الثانوية تعالج الدوران فقط (بلا تمدد/إزاحة)، ولا تصادمات، والعظام المحكومة بـIK مثبت تتجاوز مفاتيحها.
- لا يوجد بعد توقع مسار باليستي للقفز.
